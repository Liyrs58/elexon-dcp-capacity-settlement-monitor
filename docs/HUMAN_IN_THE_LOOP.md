# Human in the loop

The dashboard supports analysis. It does not approve service changes, contact customers or decide the meaning of an Elexon incident.

## What code can do

1. Generate a repeatable teaching dataset.
2. Check data structure and arithmetic.
3. Calculate queue, rate, forecast and scenario measures.
4. Rank synthetic segments for investigation.
5. Assemble a deterministic note template.

## What the analyst must do

1. Confirm the service question and deadline.
2. Check that metric definitions match the service owner.
3. Confirm data freshness, lineage and reporting window.
4. Separate public fact from hypothesis and synthetic assumption.
5. Investigate the affected workload without assigning blame from one chart.
6. Confirm customer, Settlement and payment impacts.
7. Record the owner, next update time and open questions.

## What an authorised owner must decide

1. Whether a submission should be paused, throttled or scheduled.
2. Whether work should be prioritised.
3. Whether a customer communication should be sent.
4. Whether capacity, architecture or testing work should be commissioned.
5. Whether a threshold or service objective should change.

## Visible boundaries in the project

The overview banner says that operational values are generated. The scenario page states that real controls need confirmed rules and ownership. The service note is marked as a demo template. The evidence page separates public facts from unknowns. These are deliberate controls, not decorative disclaimers.
